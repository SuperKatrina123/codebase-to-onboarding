# Design Guidelines for Onboarding Pages

The onboarding page should feel like an internal product made by a thoughtful engineering team: calm, clear, practical, and trustworthy.

## Design Goals

- Easy to scan in 5 minutes
- Deep enough to revisit in week one and week two
- Professional, but not sterile
- Structured for action, not passive reading

## Visual Tone

- Use warm or neutral backgrounds, not flashy marketing gradients
- Use one clear accent color for navigation and emphasis
- Use strong hierarchy so setup, repo map, and debug sections pop immediately
- Keep code blocks dark and readable
- Use generous spacing between sections

## Page Structure

Recommended order:

1. Hero / project snapshot
2. Day-one checklist
3. Local setup
4. Repo map
5. Core system flow
6. Common tasks
7. Debugging playbook
8. Conventions and contribution path

## Typography

- Headings should be strong and easy to skim
- Body copy should stay compact
- Labels should be short and operational
- Code should wrap instead of forcing horizontal scroll

## Layout Rules

- Prefer cards, columns, callouts, annotated trees, and step blocks
- Break long explanations into visually separated chunks
- Any list longer than 3 items should probably become cards or grouped steps
- Keep each screen focused on one practical question

## Accessibility

- Keep contrast high
- Make interactive elements keyboard accessible
- Use ARIA labels where appropriate
- Avoid relying on color alone to convey meaning

## Good Section Prompts

Each section should answer one concrete question:

- What is this repo?
- How do I run it?
- Where do things live?
- What happens during the core flow?
- Where do I change common things?
- Where do I start debugging?
- How does this team seem to work?
